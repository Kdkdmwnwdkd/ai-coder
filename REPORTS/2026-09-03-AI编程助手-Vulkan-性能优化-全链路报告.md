## 2. 时间线（一路改过来都踩过什么坑）

### 阶段 1：CPU 底包单引擎化 & 崩溃根治（已全部在前一轮完成）
- 物理删除自写 `QwenInferEngine`（C++ 推理代码），CMake 只编 `libxuedi-llama.so`（官方最简 `llama_jni.cpp`）。
- 关键踩坑：
  - **seq_max=0 的 `llama_batch_init()`** → `SIGABRT`，改 `SAFE_N_BATCH=1` + `n_seq_max=1` 根治（`v1.3.25-fix22`）。
  - **b5180 vocab API 改名**：`llama_tokenize` → 加了首个参 `llama_vocab *`；之前瞎改函数名导致 11 个编译错误，`code 55 / code 56` 连续修。
  - **EOS Guard**：前 32 步不允许 EOS（否则回答太短、跟代码到一半没了）。
  - **引擎互斥 CAS**：防止第二条消息入队 / 第一条没 cancel → 两线程同时跑 `llama_decode` 死锁。

### 阶段 2：CPU 压榨（v1.3.25-perf1 → perf1-stable → perf2-thread4）
- perf1（code 58）：三项并上
  1. `-O3 -march=armv8.2a+dotprod`（骁龙 8 Gen2 的 int8 dotprod 是硬指标）
  2. 默认 6 线程（以为 1+4+3 = 8 核全吃满更好）
  3. Prefill 批量 `llama_decode(n_batch 真 >1)` + 失败 fallback 逐条
- perf1-stable（code 59）：回滚第 3 项，因为 **b5180 + Qwen2.5 不兼容 batch Prefill** 直接崩溃（batch 切换会走 `llama_build_attn_rope`，我们约束过不能动这个函数的参数）。
- perf2-thread4（code 60）：**回退 4 线程**，因为 6 线程 3B Prefill 比 4 线程**反慢 28%**（实测 57.2s vs 32.1s），根因 = 小核 A510 和大核 A715 调度打架 + 大核带宽抢食反而拖垮 Prefill 每条 decode。
  - 🧪 这是今天所有版本的 CPU 基准：**4 线程 · 稳定**。后续任何版本，只要用户级 Vulkan 关了，就自动回到这个档位。

### 阶段 3：方案 A（Vulkan GPU）+ 方案 C（1.5B 默认快模式）一起落地（code 61 = v1.3.26-gpu1）
- 改动横跨 10 个文件 +391/-38，核心三层回退保障：
  1. **编译期**：`find_package(Vulkan)` 成功才开 `GGML_VULKAN=ON`，否则 `XUEDI_LLAMA_VULKAN=0` 全路径 CPU。
  2. **运行时**：`loadModelRobust(path, gpuLayers)` 新增关键词兜底；VULKAN / GPU / ggml_vulkan / GRAPHICS / DRIVER / ADRENO 命中 → gpuHint 立刻改 0，档位走完 CPU；4 档耗尽再补一次 L1+CPU-only。
  3. **用户级**：设置页「允许 Vulkan GPU 加速」Switch（DataStore model_store 持久化）。
- 但 Actions 上第一次编 Vulkan → `glslang + spirv-opt + vulkan-shaders-gen + ggml-vulkan 新增 CU` 跑了 35 分钟还 In progress，用户端没包 → **临时 hotfix1（code 62）**。

### 阶段 4：Hotfix1 先用 CPU 底包验证 C 方案 UI（code 62 = v1.3.26-gpu1-hotfix1）
- 把 `if(Vulkan_FOUND)` 改成 `if(0)`，`find_package(Vulkan)` 注释掉，一行强令 `XUEDI_HAS_VULKAN=OFF`，其他 A/C 代码完全保留。
- 4 分钟出 APK，通过飞书单发，用户实测拿到诊断包，对账结果见下文「6. 实测证据链」。

### 阶段 5：现在 → 真正 Vulkan 真机版（code 63 = v1.3.26-gpu2-Vulkan）
- 解了 `if(0)` 短接，恢复 `find_package(Vulkan)` 原始路径。
- Actions 正在后台编（凌晨 1 点让它跑到明天都没事）。
- **下一次开话题：第一件事就是查这个 tag 的 Release Assets >=4**，拿 APK 装，看 Prefill 247 tokens 是否 5~8s。

## 3. 改了哪些文件？（文件级索引 + 改了啥 + 位置）

> 下次要定位 Vulkan 开关 / 默认 1.5B 常量 / 线程档位 / 失败降级逻辑，直接找下面的路径和行号。

### 3.1 构建与 Vulkan 后端
1. **`.github/workflows/build.yml`**（Actions 编排）
   - `assembleRelease` → `publish-release` → `upload-mirror`（tmpfiles.org 直链 / litterbox 回退）**串行**（因为 tag push 前 release 还不存在，必须 needs publish-release，直链才不会 404）。
2. **`app/build.gradle.kts#L23-L28`**：`versionCode` + `versionName`（每次发版改这里，单调递增）。
3. **`app/src/main/cpp/CMakeLists.txt#L62-L89`**：方案 A 真正的 Vulkan 开关：
   - 现在是 code 63 版本：正常 `find_package(Vulkan) + if(Vulkan_FOUND)`，JNI 宏 `XUEDI_LLAMA_VULKAN=1`。
   - 想临时回到 CPU 底包（4 分钟出 APK）：把 `L73-L89` 改成 hotfix1 那种 `set(XUEDI_HAS_VULKAN OFF CACHE BOOL "" FORCE) + if(0)`，**一行就行**。
   - 关所有 Vulkan debug/validate/perf 开关（防止 Android 真机 Adreno driver 打印大日志拖慢）。

### 3.2 引擎层（Kotlin ↔ C++ 桥）
1. **`app/src/main/cpp/llama_jni.cpp` nativeInit**
   - 读入 4 个参数：`jPath / jN_ctx / jN_threads / jGpuLayers`。
   - 先按编译期宏钳制：`#if XUEDI_LLAMA_VULKAN==0` → `jGpuLayers` 不管多少都强令 0，保持 CPU 底包行为不变。
   - `<0 → 99`（请求全 offload，llama_init_from_model 再按模型层上限夹）。
   - `cparams.offload_kqv = (n_gpu_layers > 0)`；GPU 编译没开时不会设 1。
   - 日志行 `nativeInit: 编译未启用 Vulkan (XUEDI_LLAMA_VULKAN=0)…强制 0` / `… n_gpu_layers=99 offload_kqv=1`。
2. **`app/src/main/java/com/xuedi/coder/model/LlamaJniEngine.kt`**
   - `loadModel(path, nCtx, nThreads, nGpuLayers=-1)` 默认全 offload。
   - 新增 `loadModelRobust(path, gpuLayers)` 重载（原来只传 4 档线程）。
   - 关键词兜底：失败 error.message 命中 VULKAN/GPU/… → 后续档位强制 gpuHint=0。
   - 4 档（L1 L2 L3 L4）跑完还没起来 → **补第 5 档 L1 CPU-only**。
   - 新增字段 `lastUsedGpuLayers: Int` 供 Settings 诊断读取。
3. **`app/src/main/java/com/xuedi/coder/model/ModelPrefsStore.kt`**（DataStore model_store 独立）
   - `DEFAULT_USE_FAST_1_5B = false`（想正式启用 C 方案默认快模式，翻这一行）。
   - `DEFAULT_USE_VULKAN = true`（默认允许 Vulkan，用户设置关了就强制 0）。
4. **`app/src/main/java/com/xuedi/coder/model/ModelManager.kt`**
   - 新增 `autoSelectInitialByPrefs()`：当 Room 里 `selected == null`（用户还没手动选过），按文件名正则匹配 1.5B / 3B 自动 setSelected；只触发一次，绝不覆盖用户选择。
   - `switchAndLoadModel` 加载前读 `modelPrefs.useVulkanAccel` → 决定传 `gpuLayers = -1 / 0`。
5. **`app/src/main/java/com/xuedi/coder/App.kt` 预热流程**：在 `modelManager.getSelected()` 之前先跑 `autoSelectInitialByPrefs()`，保证首次冷启动也按偏好选档。
6. **`app/src/main/java/com/xuedi/coder/ui/screen/SettingsPage.kt` 推理偏好组**：
   - 两个 Switch：允许 Vulkan GPU 加速 / 默认使用 1.5B 快模式，`remember` + `runBlocking` 一次性读 DataStore，异步写回。
   - 切完 Toast 提示「重加载生效 / 下次冷启动生效」。
   - 诊断 ③+ 行增 `gpuLayers=CPU-only(0) / 请求全卸载(-1) / N层` 三种显示。

## 4. 三层回退保障（方案 A 绝不会把你 App 搞崩）
| 层级 | 触发条件 | 效果 | 恢复方式 |
|---|---|---|---|
| ① 用户级（最外层）| 设置关「允许 Vulkan GPU 加速」= false | 下次加载模型强制 `gpuLayers=0`，CPU-only，Prefill = 32s | 重新打开 Switch + 重新加载模型 |
| ② 运行时（引擎内）| `loadModelRobust` 抛错 message 命中 VULKAN/GPU/ggml_vulkan/… | 后续档位立刻切 CPU-only；4 档耗尽补 L1 CPU-only 第 5 档 | 无需操作，自动回退 |
| ③ 编译期（CMake）| `find_package(Vulkan)` 失败（比如 NDK runner 没 Vulkan SDK / 你本地 Android Studio 旧） | `XUEDI_LLAMA_VULKAN=0`，JNI 把任何 `nGpuLayers` 强钳到 0；ggml-vulkan 根本不会参与编译 | 升级 NDK / 装 Vulkan SDK 后重编 |
| ③+ 发布级（保底回滚）| Actions runner 编 Vulkan 超过 30 分钟卡壳 | 回到 hotfix1：把 `CMakeLists.txt#L73-L89` 改成 `set(XUEDI_HAS_VULKAN OFF ...)+if(0)`，4 分钟 CPU 底包 | 解一行注释恢复 Vulkan |

> 结论：**不管哪一层崩，用户感知最差 = perf2-thread4 CPU 底包 Prefill 32 秒**，不会坏、不会闪退、不会回到更慢的 6 线程档位。

## 5. 性能目标 & 验收标准（每条都能被日志里一行实锤）

| 项 | 目标 | 判定日志锚点（logcat -s LlamaJni LlamaJniEngine） |
|---|---|---|
